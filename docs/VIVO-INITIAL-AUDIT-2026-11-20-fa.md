# گزارش آغاز عملیات VIVO — ۲۰ نوامبر ۲۰۲۶

## وضعیت اجرایی
- مخزن کاری شناسایی‌شده: `rezameshkini2014-spec/VIVO-ONLINE`
- شاخه مبنای بررسی: `rebuild/vivo-v2`
- شاخه کاری ایزوله و تازه‌ساخته‌شده: `mission/vivo-overnight-20261121`
- شاخه‌های اصلی، پشتیبان، توسعه و بازسازی بررسی اولیه شدند.
- شاخه `main` و دو شاخه پشتیبان ۲۰ نوامبر موجودند؛ هیچ‌کدام در این مرحله تغییر داده نشده‌اند.

## یافته‌های تأییدشده از بررسی کد
1. رابط قدیمی در `index.html` و نسخه بازسازی‌شده در `vivo-v2.html` / `vivo-v2.js` وجود دارند؛ نسخه بازسازی‌شده فایل‌های CSS مستقل نیز دارد.
2. رابط قدیمی بخش عمده حساب، گفتگو و پیش‌نویس‌ها را در `localStorage` نگهداری می‌کند. در همان رابط، مرکز ربات‌ها صریحاً پیش‌نویس محلی و غیرفعال است؛ بنابراین نباید به‌عنوان ربات واقعی معرفی شود.
3. در رابط قدیمی، صفحه حریم خصوصی اعلام می‌کند برخی ترجیحات فقط محلی‌اند و هنوز روی سرور اعمال نمی‌شوند؛ بخش نشست‌های چنددستگاهی نیز هنوز متصل نشده است.
4. شاخه بازسازی شامل API سمت سرور برای نشست و پراکسی به Supabase Edge Function است؛ نشست با کوکی HttpOnly/Secure/SameSite تنظیم می‌شود.
5. تابع ابری `supabase/functions/vivo-api/index.ts` مسیرهایی برای گفتگو، پیام، واکنش، ویرایش/حذف، گروه، خوراک اجتماعی، پست، نظر، دنبال‌کردن، استوری، اعلان، مسدودسازی، گزارش و پروفایل دارد.
6. سه migration پایگاه داده در `supabase/migrations` وجود دارد: هسته اجتماعی، پیش‌فرض‌های حریم خصوصی و همکاری گفتگو.
7. OTP در مسیر فعلی بر Web Push متکی است، نه پیامک. مستندات سرویس OTP جداگانه نیز همین محدودیت را تصریح می‌کنند؛ پس تأیید شماره تلفن از طریق Push را نباید معادل ارسال SMS دانست.
8. در نسخه قدیمی، ارسال پیام در تابع محلی `send()` به آرایه گفتگو اضافه و در `localStorage` ذخیره می‌شود؛ این به‌تنهایی پیام‌رسانی بلادرنگ یا ارسال بین دو حساب مستقل را ثابت نمی‌کند.
9. در کدهای بازیابی‌شده، بخش‌هایی از رابط به‌صراحت عملکردهای محلی/غیرفعال را اعلام می‌کنند. این موارد باید پیش از هر ادعای «کامل» به API واقعی متصل و بین دو حساب آزمایش شوند.

## ریسک‌ها و موارد نیازمند بررسی تکمیلی
- باید مشخص شود Vercel در حال حاضر کدام شاخه و کدام فایل ورودی را منتشر می‌کند؛ وجود URL زنده به‌تنهایی اتصال آن به شاخه بازسازی را ثابت نمی‌کند.
- باید وضعیت متغیرهای محیطی، پروژه Supabase، Edge Function منتشرشده، schema واقعی دیتابیس، RLS و storage بررسی شود؛ مقدار هیچ secret در گزارش ثبت نمی‌شود.
- باید جریان OTP و ثبت‌نام از ابتدا تا انتها با دو حساب آزمایشی بررسی شود.
- باید مسیر واقعی ارسال و دریافت پیام، فایل، اعلان و ارتباط بین کاربران آزمایش شود.
- باید مطابقت رابط و API و رفتارهای حریم خصوصی، به‌ویژه مخفی‌بودن تلفن/ایمیل و جست‌وجوی دستی شناسه، بررسی شود.
- فایل لوگوی اصلی در فهرست ریشه مخزن بازسازی‌شده دیده نشد؛ تا یافتن asset اصلی، هیچ لوگوی جایگزینی نباید ساخته یا جایگزین شود.

## قواعد ادامه عملیات
- تغییرات فقط روی شاخه کاری ایزوله انجام شوند؛ شاخه‌های `main` و پشتیبان‌ها دست‌نخورده بمانند.
- قبل از هر ادعای تکمیل، معیار پذیرش و آزمایش قابل تکرار ثبت شود.
- قابلیت فاقد backend یا تست واقعی باید «طراحی‌شده»، «محلی»، «آزمایشی» یا «غیرفعال» برچسب بخورد، نه «تکمیل‌شده».
- تصمیم‌های قطعی محصول درباره حریم خصوصی و مخاطبان بدون تأیید مالک تغییر نکنند.
- انجمن‌ها و کیف پول به محصول افزوده نشوند.

## وضعیت این گزارش
این سند فقط گزارش ممیزی اولیه مخزن است؛ هنوز ادعای تست end-to-end، استقرار جدید، تکمیل قابلیت‌ها یا بررسی secrets مطرح نمی‌کند.
